# cbindgen Header Not Verified in CI

**Severity:** Medium
**Category:** Build integrity — Header/source drift
**Status:** Yellow — committed header with no staleness check

## Summary

The `defra.h` C header is generated by cbindgen and committed to the repository root, but no CI step verifies that the committed header matches what cbindgen would generate from the current source. If a developer modifies FFI function signatures without regenerating the header, the committed `defra.h` becomes silently stale, causing undefined behavior when Go code links against the Rust library.

## Affected Files

- `defra.h` (repository root, 1657 lines) — committed generated header
- `crates/ffi/cbindgen.toml` — cbindgen configuration
- `crates/ffi/Cargo.toml:67` — `cbindgen = "0.28"` in `[build-dependencies]`
- `.github/workflows/ci.yml` — no header verification step
- `.github/workflows/release.yml:264-265` — generates header as release artifact

## Details

### Current Architecture

The cbindgen workflow has two modes:

1. **CI/Release builds:** The release workflow runs `cbindgen --config crates/ffi/cbindgen.toml --crate ffi --output defra.h` to generate the header as a release artifact. This is correct.

2. **Development:** Developers must manually regenerate `defra.h` after changing FFI function signatures. There is no build.rs that auto-generates the header (despite cbindgen being listed as a build-dependency, no `crates/ffi/build.rs` exists).

### The Gap

If a developer:
1. Adds a new `#[no_mangle] pub unsafe extern "C" fn` to the FFI crate
2. Forgets to run `cbindgen` to regenerate `defra.h`
3. Commits and pushes

The committed `defra.h` will be missing the new function. Go code using the old header will compile but won't be able to call the new function. Worse, if a function signature changes (parameter types, return type), Go code compiled against the stale header will have ABI mismatches leading to memory corruption.

### cbindgen Configuration Review

The `cbindgen.toml` explicitly includes only these types:
```toml
[export]
include = ["FfiResult", "NewNodeResult", "NewTxnResult", "NodeInitOptions"]
```

This is a **positive security control** — only explicitly listed types are exported to the C header. Functions are included automatically based on `#[no_mangle] pub extern "C"` annotations.

### Unused Build Dependency

`cbindgen = "0.28"` is listed in `[build-dependencies]` but there is no `crates/ffi/build.rs` to use it. This dependency is downloaded and compiled during builds but never invoked. It should either be removed (if generation is always manual) or a build.rs should be created to auto-generate the header.

## Remediation

Add a CI check that regenerates the header and verifies it matches the committed version:

```yaml
  verify-header:
    name: Verify FFI Header
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - run: cargo install cbindgen
      - run: cbindgen --config crates/ffi/cbindgen.toml --crate ffi --output defra-generated.h
      - run: diff defra.h defra-generated.h
```

Also either:
- (a) Remove `cbindgen` from `[build-dependencies]` since it's unused there, OR
- (b) Create `crates/ffi/build.rs` that auto-generates the header into OUT_DIR

## Exploitability

Not directly exploitable by an external attacker, but ABI drift between the committed header and actual FFI functions would cause undefined behavior in Go consumers. This is a correctness and safety issue, not a confidentiality issue.
